The Normalization Model

Every source maps
to the same scale.

Raw data from third-party platforms arrives in inconsistent shapes — Likert scales, binary flags, rate counts, timestamps. The normalization engine converts every input to a common 0–100 scale before it touches the scoring model. A 72 from Mobaro means exactly the same thing as a 72 from a native AS 360 audit.

01
Schema Mapping
Each connector declares a field map — a translation table that converts the source platform's field names to AS 360 stream identifiers. A Mobaro checklist.pass_rate becomes stream.readiness.pre_open_compliance.
// Mobaro field map
"mobaro.checklist.pass_rate"
→ "as360.stream.R.pre_open_compliance"

"mobaro.downtime.duration_hrs"
→ "as360.stream.I.equipment_availability"
02
Type Coercion
Every source uses different value types. Binary pass/fail becomes a rolling pass rate over the observation window. A severity code becomes a weighted penalty score. A timestamp gap becomes a response time metric in minutes.
// Binary → pass rate
[pass, pass, fail, pass, pass]
→ 80.0 (4/5 pass rate)

// Severity code → penalty
severity_code: "P2"
→ penalty_score: -18.5
03
0–100 Conversion
After coercion, every stream value is mapped to 0–100 using the stream's calibration function. Pass rates rescale linearly. Rate-based streams like incidents use a penalty-decay model where more events push the score toward zero. Continuous sensor feeds use range normalization.
// Linear rescale
pass_rate: 0.80 → score: 80

// Penalty-decay (incidents)
incidents_per_1000: 2.4
→ score: 100 × e^(-0.3 × 2.4)
→ score: 48.7
04
Pillar Assignment
Each normalized stream value is assigned to a pillar — Readiness, Integrity, Delivery, or Environment for RIDE Score; Safety, Protocol, Lifeguard, Aquatic, Structure, or Hazard for SPLASH. The pillar score is the weighted average of all assigned streams in that pillar.
05
Source Disclosure
Every score record carries its data provenance — which streams came from which sources, what the update cadence was, and what the confidence level is. An underwriter can see that the Integrity pillar score is weighted 40% native AS 360, 35% Mobaro, and 25% state inspection records. Transparency is the product.

Technical Architecture

How a connector
actually works.

Each connector is a standalone Cloudflare Worker. It runs on a schedule, authenticates with the source platform, fetches new records since last sync, normalizes them, and writes to the AS360 Airtable base. The entire ingestion path runs serverlessly with no infrastructure to manage.

01
Scheduled Trigger
Cloudflare cron triggers fire each connector Worker on the appropriate cadence — every 15 minutes for real-time platforms, hourly for API polling, nightly for batch exports and state database scrapes.
02
Authenticated Fetch
Each Worker stores API keys and OAuth tokens in Cloudflare Workers KV (encrypted at rest). On trigger, it authenticates and requests records updated since the last successful sync timestamp — incremental, not full re-ingestion.
03
Schema Translation
The field map is a JSON config stored per connector. Each record is run through the map — renaming fields, converting types, applying the 0–100 normalization function for each stream. Records that fail validation are logged to an error queue, not silently dropped.
04
Airtable Write
Normalized records write to the External_Ingestion_Log table with full provenance metadata — source platform, connector version, ingestion timestamp, raw value, normalized value, and stream assignment. The scoring engine reads from this table alongside native AS 360 audit records.
05
Score Recalculation
After each ingestion batch, an Airtable automation triggers the scoring recalculation. New stream values flow into their pillar aggregates and the composite score updates. MGR dashboard reflects the change within 60 seconds of source data being available.
// Mobaro connector — Cloudflare Worker
// Runs every 15 minutes via cron trigger

export default {
async scheduled(event, env) {
// Get last sync cursor from KV
const lastSync = await env.KV
.get('mobaro:last_sync');

// Fetch updated records from Mobaro API
const records = await fetchMobaro({
endpoint: '/v2/inspections',
since: lastSync,
apiKey: env.MOBARO_KEY
});

// Normalize each record
const normalized = records.map(r => ({
source: 'mobaro',
stream: FIELD_MAP[r.type],
raw_value: r.pass_rate,
score: normalize(r.pass_rate, 'linear'),
ride_id: r.attraction_id,
timestamp: r.completed_at
}));

// Write to AS360 Airtable base
await writeAirtable(
'External_Ingestion_Log',
normalized
);

// Update cursor
await env.KV.put(
'mobaro:last_sync',
new Date().toISOString()
);
}}
Design Principles

Why this architecture
earns trust.

🔍
Full Provenance
Every score record carries its data lineage. An underwriter can see that the Integrity pillar is 35% Mobaro records, 25% state inspection data, 40% native AS 360 audits. No black box. No unsourced numbers. Complete audit trail from raw source to composite score.
⚖️
No Single Source Controls
The normalization architecture is designed so that no single platform — including native AS 360 tools — can dominate the composite score. A park that games one source sees the divergence flagged when other sources disagree. Triangulation is the architecture, not a feature.
🔒
Data Stays Yours
Connector access is authorized by the operator or facility on behalf of their own data. AS 360 processes on behalf of the subscriber — not independently. A data processing agreement governs each connector. Raw source data is not stored. Only normalized stream values and provenance metadata are retained.
📡
Source-Agnostic Scoring
The RIDE Score engine does not know or care whether a stream value came from Mobaro or a native AS 360 audit. After normalization, all inputs are structurally identical. A park with Mobaro can generate a score on day one. A park with no existing platform uses native tools from day one. Same score model. Same output.
🏗️
No Rip and Replace
The aggregation architecture is a deliberate commercial decision. Asking a park to abandon their existing tools is the fastest path to a lost deal. AS 360 sits on top of what already exists. The connector library grows over time. The moat deepens with every source we ingest.
📈
Better Data Over Time
Every connected source that runs for 30+ days generates a historical baseline. At 90 days you have a trend line. At 12 months you have seasonal patterns. The score improves not because the algorithm changes but because the data depth increases. Long-term deployments generate fundamentally richer signals than point-in-time audits.
